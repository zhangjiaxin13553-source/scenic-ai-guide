## 1. 关键判断：阶段四到底部署什么

先厘清一个容易跑偏的问题。README 和早期方案里写的阶段四是「模型蒸馏、量化压缩、Jetson 边缘设备部署」，**这个提法已经过时了**——因为我们的 LLM 根本没在本地跑。

| 组件 | 跑在哪里 | 阶段四要做什么 |
|------|---------|--------------|
| **LLM 生成** | ☁️ 云端 API（DeepSeek v4-flash） | 无需部署，只需保证网络可达 + Key 安全注入 |
| **BGE 嵌入模型** | 💻 本地（`scripts/bge-small-zh-v1.5/`，~100MB） | 需要随软件一起打包分发到机器人设备 |
| **ChromaDB 向量库** | 💻 本地（`chroma_db/`） | 需要打包分发（或现场重建） |
| **对话管线 + 质量守卫** | 💻 本地 Python | 核心部署对象，封装成 API 供机器人调用 |
| **语音 ASR / TTS** | 🤖 机器人硬件层（实验室提供） | 我们只提供对话 API + 对接协议，不做语音 |

**结论**：阶段四的本质是**「软件 API 化 + 环境固化打包 + 语音接口对接 + 演示准备」**，
不是模型量化。这四点才是把「大脑」真正装进机器人并扛住演示的关键。

        │  POST /chat  {text}              │
        │      │                           │

## 4. API 接口设计（机器人对接协议）

这是阶段四的**核心交付物**——机器人控制层与我们软件的契约。

### 4.1 接口清单

| 接口 | 方法 | 用途 |
|------|------|------|
| `/chat` | POST | 单轮对话：文本进 → 回复出（机器人主调用） |
| `/health` | GET | 健康检查：模型/向量库/熔断器状态（机器人启动时探活） |
| `/reset` | POST | 清空对话历史（机器人切游客/结束一轮时调用） |

### 4.2 请求 / 响应格式

```jsonc
// POST /chat
// 请求
{ "text": "鲁迅先生，您为什么弃医从文？", "session_id": "tourist-001" }

// 响应（成功）
{
  "success": true,
  "reply": "……（鲁迅口吻回答）……",
  "intent": "luxun",              // narrator | luxun | ambiguous | reject_time | reject_irrelevant
  "mode": "🎭 鲁迅数字人",          // 给人看的中文标签，机器人可忽略
  "guard_status": "PASS",         // PASS | WARN | AMEND | FALLBACK
  "latency_ms": 1800
}

// 响应（失败兜底——接口不抛错，永远返回可播报文本）
{ "success": false, "reply": "这大约是什么缘故呢……请你稍后再问罢。", "latency_ms": 120 }
```

### 4.3 关键设计原则

- **永不返回 5xx 空响应**：任何内部异常都转成鲁迅/讲解员口吻的兜底文本，机器人 TTS 永远有词可播。
- **`session_id` 可选**：本轮 demo 主要单轮问答，多轮历史按会话隔离（不做则全局限单会话）。
- **超时对齐**：接口层设置与 `llm_client.py` 一致的超时（默认 30s），超时走兜底，不阻塞机器人。

### 4.4 为什么用 FastAPI 而不是直接用 Gradio

- Gradio 是**人机调试界面**，它的 API 是附带能力，对机器人的稳定性和错误语义不友好。
- FastAPI 是**正经 REST 服务**：类型校验、自动文档（`/docs`）、明确的 HTTP 状态码、可被机器人控制层（任意语言）稳定调用。
- **两者并存**：FastAPI 给机器人用，Gradio 保留给现场人工演示/调试用，共用同一个 `RAGPipeline` 实例。

## 5. 端侧部署方案

### 5.1 部署形态（推荐：单机进程，LLM 走云端）

| 决策点 | 推荐 | 理由 |
|--------|------|------|
| LLM 是否本地化 | ❌ 不本地化，保持 DeepSeek 云端 | 本地跑 70B 量级 LLM 不现实；云端 v4-flash 已 1.5s 达标 |
| 边缘设备 | 机器人自带的 Jetson / 一台 PC 均可 | 本地只跑 BGE(~100MB) + ChromaDB + Python 管线，CPU 即可，无需 GPU |
| 服务形态 | 单个 FastAPI 进程 + 内置 Gradio（可选） | 简单可控，减少现场故障面 |
| 网络要求 | 设备需能访问 `api.deepseek.com` | 若现场断网，需降级预案（见 §7 风险） |

### 5.2 延迟预算（语音对话目标 <2s）

当前基线：**平均 3.7s/条**（来自 90 题 eval）。拆解与优化路径：

| 环节 | 当前耗时 | 优化手段 | 优化后 |
|------|---------|---------|--------|
| BGE 检索 | ~50ms（有缓存） | 预热 + 保持缓存 | ~30ms |
| DeepSeek 生成 | ~1.5s | 已是直答模式，无空间；可用 streaming 把**首字延迟**压到 <1s | 首字 <1s |
| 意图分类 + 改写 | ~几十 ms | 已纯规则/缓存 | 不变 |
| 幻觉 + 一致性检查 | ~0.5-1s | 语义比对缓存、精简 NER 范围 | ~0.3s |
| 模型冷启动 | 首次 ~10s | **进程常驻预热**，启动即加载 | 均摊为 0 |

> 关键认知：语音场景用户感知的是**首字延迟**而非完整回答耗时。若时间允许，给 `/chat` 加 SSE 流式返回（首字 <1s 出词，边生成边播报），体验提升最大。**但这是可选优化**，demo 保底先做「预热 + 精简检查 + 缓存」，把 3.7s 压到 2s 附近。
